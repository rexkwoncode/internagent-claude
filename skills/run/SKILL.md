---
name: run
description: Run pinned InternAgent or MLEvolve using the original Python workflow and Claude Code for model requests.
argument-hint: "[options.json|task-id|task-folder] [mailbox-directory]"
---

Arguments: $ARGUMENTS

Use the original upstream Python engine. Prepare the runtime for the user's trusted task. Use one of these inputs and preserve the user's selected engine and settings.

- With an options JSON, use its `engine`, pinned `checkout`, optional `python`, optional InternAgent `config`, and upstream `args`. For ML search within an InternAgent research run, preserve its nested `mlevolve` backend settings. Keep `engine` set to `InternAgent` for that workflow. With no arguments, load `internagent-upstream.json` in the project root if available. Otherwise use the task established in the conversation or ask for the task.
- With an upstream task ID or task directory, use InternAgent. Reuse the pinned full checkout from project options when available, or obtain it with `node "${CLAUDE_PLUGIN_ROOT}/scripts/upstream.mjs" InternAgent <checkout>`. Resolve a catalog ID to the corresponding task folder, fetching the pinned ResearchClawBench task when applicable. For paper tasks also ensure the full pinned nested `sci_tasks` checkout is initialized so the judge can import its evaluator. Write run-specific options under .internagent with explicit absolute `--task` and `--output_dir` arguments. Preserve the runtime options if provided. A paper reproduction uses experiment mode. A question with no evaluator can use `--mode report` when that matches the task.
- With `report <task-id|task-folder>`, prepare the same upstream task options and set `--mode report`. For an upstream resume, reuse the original options with `--resume <absolute-launch-directory>` in the argument array and use a fresh mailbox.
- If given an existing lightweight task JSON, the Node demo, or a lightweight checkpoint, use `internagent:lightweight` only when the user's input explicitly selects that format or workflow. Never switch workflows because an upstream dependency is missing.

Use absolute paths in upstream launcher arguments. For dependencies and settings consult `${CLAUDE_PLUGIN_ROOT}/docs/upstream-runtime.md`.

1. Read the options and get effective model aliases with `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" models` from the project root. Use a fresh mailbox directory such as .internagent/upstream-runs/<id>. Start `node "${CLAUDE_PLUGIN_ROOT}/scripts/upstream-run.mjs" start <mailbox> <options.json>` in a background shell job, retaining its task ID or log location. Do not run a second copy if the first is still working.
2. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/upstream-run.mjs" pending <mailbox>`. It waits up to 20 seconds. If no requests arrive, check whether the background task finished early and inspect its output for preflight errors. Repeat while the upstream process is active. Use the returned request metadata to delegate by path. Read a request directly when its workspace is needed for a builder or when debugging a rejected response.
3. Delegate model requests to `internagent:upstream-model` with the request path and the correct Agent tool `model` parameter. Use an explicit configured Claude alias if present in the request. For configured-reviewer use the persistent reviewer alias and for configured-builder use the persistent builder alias. For configured or bundled model names, use the persistent planner alias for reasoning and builder alias for code generation or workspace edits. For `inherit`, omit the argument. Multiple pending requests may be delegated concurrently. When the upstream model requests a supplied tool, the worker returns the requested invocation as data. For kind experiment, delegate instead to `internagent:builder`. Give it the request path and the exact upstream workspace as its writable directory. Explain that upstream will run the evaluator and that it should preserve task inputs and return an implementation or report summary. Honor completion markers stipulated in the upstream prompt only when the step is actually complete.
4. Write the worker's response as UTF-8 JSON to a scratch file in the mailbox. Text and structured answers use `{"value":...}` with a string or structured object matching the request. A messages response has a value object with a content string, or tool_calls containing objects with name and arguments (an object). If blocked, submit `{"error":"<specific reason>"}`. Call `node "${CLAUDE_PLUGIN_ROOT}/scripts/upstream-run.mjs" respond <mailbox> <id> <response.json>` with the inputs quoted separately, then poll for the next request.
5. Wait for the reported process result. Review upstream logs and summarized output paths. Report which upstream features ran and which failed preflight or require additional dependencies. For resume use the upstream resume argument and a fresh mailbox. Confidential inputs can appear in mailbox files, so keep the mailbox local and out of tracked source.
