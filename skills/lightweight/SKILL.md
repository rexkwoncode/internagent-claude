Arguments: $ARGUMENTS

Use the user's Claude Code session and the native internagent:planner, internagent:builder, and internagent:reviewer agents. Use this skill when the user requests a run, build, or resume. Perform the run during this session. Call the runner from the project root so it can find persistent project settings. Runner: node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs".

Run each runner command as its own shell tool call with the literal quoted script path. Shell variables, pipelines, and compound calls can require extra permissions in scripted sessions.

Use the resolved `models` map returned by the runner's init or status for every Agent call for this task. For each planner, builder, or reviewer invocation, set the Agent tool's `model` argument to the corresponding alias. For `inherit`, omit the argument so the agent uses the current session model. Passing an alias in prompt text does not select it. If an explicit alias is configured and the Agent tool lacks a model argument, rejects the alias, or reports a replacement, stop and report the issue. Keep the configured policy on resume.

1. For a task JSON, inspect the objective, constraints, seed, evaluator invocation, resource budget, and candidate contract. Include task constraints in the planner and builder delegations and preserve them on resume. Use the supplied run directory or choose a fresh .internagent/runs/<id>. For demo, use "${CLAUDE_PLUGIN_ROOT}/examples/regression/task.json"; use five trials to minimize MSE, with train(rows) returning predict(x). The target may be nonlinear. The bundled path can go directly to init, which returns the task summary. Leave evaluator fixtures and coefficients unread by the builder and planner. For resume, the second argument is the existing run directory. Quote every path as a separate shell argument.
2. Initialize with `init <task.json> <run> discovery` once. For a resume or after compaction, read `status <run>` and the run's state and prior notes. Skip init if resuming. Use `recall .internagent/runs "<objective>" "<current-run>"` to retrieve related trial notes and supply useful evidence to the planner. Treat historical scores as comparable only when their evaluator and split match.

For `algorithm-engineering` tasks, frame hypotheses around algorithmic work, representation, locality, or parallelism as appropriate. Record what would disconfirm each hypothesis, then use measured results to guide the next design. Give the builder the correctness contract before asking for performance changes. A candidate must pass the fixed correctness check before timing. Keep inputs, warmups, repetitions, and hardware settings fixed for comparisons. In the report distinguish asymptotic analysis from measured performance, include per-workload evidence and machine/runtime details when available, and qualify speedups when variation is large. Compare holdout scores only against measurements on the same holdout workload.

3. Until done, run `next <run>`. When it requests a discovery phase, follow the phase instructions below and call `next` again. When it returns a trial, use its mode, candidate directory and parents. Run the baseline unchanged. For a draft with a recorded hypothesis, give that hypothesis and its method to the builder. For a legacy draft without one, ask the planner for an independent idea. For improve and evolve, give the planner the selected parent's results and the full recorded trajectory identified by the evidence IDs, including failed attempts. For evolve, ask for a substantially different way to address the branch's bottleneck. For debug, focus on the specific failure and its logs. For fusion, ask the planner to identify complementary measured changes and give the builder both parent paths. For every non-baseline trial delegate to internagent:builder with the assigned path and precise change. If a resumed pending candidate already contains work, inspect it before editing further. Preserve previous trial trees, evaluator, task spec, original project, and holdout.
4. Run `evaluate <run> <id> "<one-line hypothesis and implementation>"`. Use the runner's machine-recorded score and logs. Do not handwrite metrics. A failed trial consumes one slot, and the runner may schedule a debug child. Stop on baseline failure and report the logs. Keep going on candidate failures within the trial budget.
5. Ask internagent:reviewer to audit the proposed winning candidate and validation evidence. If the audit shows an invalid comparison, report it and start a corrected run only if authorized. Otherwise run `finish <run>`, which holds candidate selection fixed and optionally evaluates the configured holdout. Distinguish a failed holdout from a successful final measurement. Do not tune from the holdout.
6. Write report.md under the run with the objective, requested model aliases by role, baseline and winner metrics, absolute delta, trial table with lineage, round-by-round idea choices, failed hypotheses, holdout result, and winning candidate and artifact paths. State how to reproduce the winning result. If blocked by permissions, name the specific tool permission and leave the run resumable.

## Discovery phases

Use the role's resolved model and delegate each requested phase separately. Read the current round from `status` for the earlier artifacts. Give the agent the task contract, its round baseline path, and relevant measured results from earlier rounds. In a fresh round the code starts at the original baseline. In an incremental round it starts at the best previous candidate. Both can learn from earlier results. Supply any configured seed ideas and feedback. Keep withheld inputs unread. All artifacts include the integer `round` returned by `next`.

- **generation** uses the planner. Generate competing ideas about different mechanisms using the task, permitted inputs, previous successes and failures, recalled notes, and user seed ideas. Request at least `count` ideas and preferably a few more, with at most 24. Return `ideas`, an array of objects with unique lowercase slug `id`, `title`, `hypothesis`, and a falsifiable `test` under the fixed evaluator.
- **critique** uses the reviewer. Reflect on the assumptions and failure modes of each idea. Gather relevant external evidence with Claude Code's available research tools when it can inform the comparison, then supply the sources to the reviewer. Compare against the baseline, earlier results and cited works. Report gaps when lookup is unavailable. Return `reviews`, with exactly one object per generated idea containing `id`, `assessment`, and any verified source URLs in `sources`.
- **evolution** uses the planner. Revise, recombine, or replace ideas in response to the critique, sources, and prior experiments. Keep multiple distinct approaches. Return `ideas` in the generation schema with at least `count` entries. Use an optional `parents` array of generated idea IDs to record ancestry and explain substantial changes in the hypothesis.
- **ranking** uses the reviewer. Rank every evolved idea on evidence, plausibility, novelty relative to the baseline, feasibility within the budget, measurable impact, and diversity of the selected set. Return `ranking`, a best-first array with each evolved `id` once and a `reason` for its position. These are judgments about which experiments to run. Actual validation scores determine the winner.
- **methods** uses the planner. Take the first `count` ranked ideas in order. Make each implementation and experiment plan concrete, including what to change, what to keep fixed, and what would disconfirm it. Return exactly those IDs in rank order in `ideas`, using the generation fields and a `method` string.

Ask the agent to return the JSON object. Check it and write it under the run directory with the round and phase in its filename. Call `stage <run> <phase> <artifact.json>`. Correct rejected artifacts before continuing. The runner saves each accepted phase in state.json. When supplied ideas were configured to bypass generation, the runner issues the drafts directly.
